# Historical data coverage (History app)

Atlas's **History** app displays route frequency changes over a 10-year period. This document details the history model, the status of audited systems, and deferred agencies.

---

## History model & eligibility

For an agency to show up in the History app, it must satisfy both of these:
*   **Distinct Years** (frontend eligibility): Must have at least **10 distinct years** across its route snapshots and any `history/{slug}/coverage.json` coverage years (`MIN_HISTORY_DISTINCT_YEARS = 10` in `shared/historyEligibility.ts`). This is the default rule and is unchanged. Under History v2 (`ATLAS_HISTORY_V2=1`, passed by the build as `realYearsOnly: true`) only **real snapshot years** count, none after the build year, and `coverage.json` years are ignored (this shrinks the public list from 22 to 16 agencies, so it is not on by default).
*   **Change Detection** (`pipeline/build-history.ts`): Must have at least **1 route** with a recorded headway change that differs from current live data before it is compiled into the history config at all.

### History v2 is opt-in: one flag, `ATLAS_HISTORY_V2=1`

History v2 is **flag-gated, not additive**. `refresh-feeds.yml` runs `build-history` every Monday and writes the public `history-config.json`, so with `ATLAS_HISTORY_V2` unset (the cron) the build output is **byte-identical to the pre-v2 build** (`pipeline/__tests__/buildHistoryDefaultGolden.test.ts` compares it with a golden made by origin/main's own `build-history.ts` on a synthetic multi-agency fixture). Only the exact value `1` turns v2 on. Every v2 behaviour below runs only behind it:

*   **Build (`pipeline/build-history.ts`)**: the sidecar join, alias merging, one snapshot per route per year, dropping future/blank-label/unparseable snapshots, the representative all-day value (and no `directionId` filter) on the current endpoint, skipping the current endpoint for limited routes, the build report (`tmp/history-build-report.json`) and visibility checks. Unset, the build reads no sidecars or alias file, writes no report, and keeps the old fastest-direction-0 current value.
*   **Eligibility (`shared/historyEligibility.ts`)**: an explicit option `realYearsOnly` (default `false` = the original rule), not an env read, because the file also runs in the browser. The build passes `realYearsOnly: v2` when it rewrites `shared/data/history-agencies.json`, so by default that file is written exactly as before.
*   **Route keys (`pipeline/historyRouteKey.ts`)**: the long-name fallback is the option `longNameFallback`, defaulting to the env flag, so a normal refresh creates no new keys. v2-only code (`historyV2.ts`, `historyWeekend.ts`, `backfill-history-v2.ts`) passes it explicitly. The legacy backfills (mdb, gcrta, cdta, mbta, norta) use `backfillRouteKey`: by default they skip a blank short name as they always did; under the flag they use the full key function.
*   **Writers (`pipeline/refresh.ts`)**: sidecar writes and the weekday/Saturday/Sunday fingerprint in `latest.json` run only with the flag (unchanged).
*   **Pilots**: run with `ATLAS_HISTORY_V2=1` set in the environment.

### History v2 snapshots (versioned; applies only with the flag)

Each v2 snapshot carries `v2: {refDate, key, rep, sat?, sun?, flag?}`; old snapshots stay as they are.

*   **Real date.** `refDate` is the service day the processor read (the same auto-detected reference date as the map). A v2 snapshot's `year` is the year of `refDate`; an old snapshot keeps the year of its period key. At build time every snapshot whose year is after the build year is dropped (no archive file is rewritten).
*   **Dropped snapshots are reported.** The build also drops any snapshot with an empty or unparseable label, an unreadable `refDate`, or no year, and lists each in `tmp/history-build-report.json` (slug, route, label, reason).
*   **One per route per year.** Snapshots group by (route key, year). The winner is the latest `refDate` (when both have one), else the latest period key, then `processedAt`. If two disagree by more than 25% the later is kept and the build report counts it. Snapshots are ordered by real date, never by month-name labels.
*   **Representative weekday value.** `rep.h` is the route's all-day value (`routeAllDayHeadway`: worst direction, main-stretch median, settled rules), never the fastest pattern or direction 0. The no-service sentinel (or a route whose rows are all `span`) is stored as `rep.lim`, with no number. No stamp means blank. `rep.p` holds the per-period values (`routeFilterHeadwayByPeriod`, else `worstDirectionHeadwayByPeriod`). A limited or blank v2 snapshot is dropped from the published list rather than filled from an old pattern minimum.
*   **Weekend.** `sat` / `sun` are optional; a missing key is unknown (blank), never 0. `{none:true}` is stored only when the feed's calendar proves it (`pipeline/historyWeekend.ts`): the reference week is inside the calendar window, calendar.txt has rows, none of the route's services flags the day and none is added on that weekday, the route has weekday service, and either other routes run the day or nothing in the feed does or adds it. Expired or non-covering calendars stay blank, and a one-day holiday row never counts as Saturday service.
*   **Flags.** `flag` is `fast` (under 2 min), `slow` (over 300 min) or `limited`. Stored only; nothing is hidden anywhere.
*   **Keys.** `historyRouteKey` (short name, else route_id, else, under v2 only, long name) is the only key function; no backfill skips a route inline because of a blank short name (a test enforces it; they go through the flag-gated `backfillRouteKey`). The display name is the long name, then the key.
*   **Aliases.** `config/history-route-aliases.json` (`{slug: {canonicalKey: [oldKeys]}}`) folds old keys into the canonical key before the one-per-year rule. Only aliases verified from data go in (route_id continuity plus matching descriptions and termini). Current entries are LA Metro (`lacmta`): 2/302, 30/330, 108/358, 111/311, 51/52/352, 78/79/378, 163/162 and 245/244 (both id changes happened in 2021). Caveats: `30/330` may include limited-stop 330 trips from the old combined route; `245/244` has an odd 2020 value (61 min against 36 before and 30 after). Parked for Ryan, not aliased: the combined 16 keys (16/316, 16/17/316, 16/17) and the Rapid lines (733, 760, 705). Detroit (`ddot`): 046 to 46, 023 to 23, 060 to 60, 049 to 49 (the leading zero was only used in the 2016 to 2019 feeds; same route name, route corridor and termini, and the two spellings never run in the same feed). Caveats: 46 lost its Saturday service and half its trips in 2017; 23 and 60 had terminus changes (Northland Center to Meijer Gateway; Northland Center to Evergreen & Ten Mile); 49 ends in 2017 (no current route). Parked for Ryan, not aliased: ddot 9 (the pair 9/025 is not one route: 9 was Chalmers in 2014 and 2016, Jefferson from 2018, while Jefferson was 25, then 025, then 009; folding them would collide in 2014 and 2016) and caltrain Local into Local Weekday (same all-stops service, but the old Local also carried weekend trips, so its Saturday and Sunday values would land on a weekday-only route). STM Montreal (`stm`): 19 to 20 (Chabanel / Marche Central became Crémazie / Marche Central; 19's last service day was 2026-05-17 and 20 starts 2026-05-18, so they never run together). Caveats: STM route_ids equal the short names, so there is no route_id continuity to check; the Marche Central end was rerouted and extended (about 60% of 19's stops carry over). Parked for Ryan, not aliased: 715 to 50 (same name, but only about half of 715's stops carry into 50 in 2025 and by 2026 both ends differ), 435 to 480 (480 serves about half of 435's stops, the downtown half of the old Du Parc express), 191 to 198 (191 Lionel-Groulx to Dorval became 198 Angrignon to Dorval; 491 is its own route since 2015, not a successor), 419 to 210 (express with a Fairview terminus became a local with an Anse-a-l'Orme terminus; clean handoff 2026-05-18). Not aliased, because both keys ran as separate routes in the same feed years: 58/61, 15/34, 53/55, 146/13, 405/211, 968/174. No successor found: 77, 78, 76, 109, 425, 495. Route 70 changed name from Bois-Franc to Poirier in 2026 but is the same route (same key, same Côte-Vertu to Raymond-Lasnier line), so no alias is needed.
*   **Holiday-week reference dates are dropped (blank beats wrong).** The shared reference-date picker can land on a holiday-week day at the end of a calendar_dates-only feed (STM's Oct 2024 dataset read Sunday 2025-01-05; its weekday reading used Dec 25 / Jan 1 timetables: 20 of 153 routes were at least 1.5x both neighbours, e.g. route 14 at 51 min against 27 before and after). The 5x spike check misses this. The sidecar writer (`refresh` and `backfill-history-v2.ts`, which know the zip) now stores an optional, additive `refDateQuality: {holiday, reason, tripsOnRef, medianTrips}` computed by `pipeline/historyRefQuality.ts` from `calendar.txt`, `calendar_dates.txt` and `trips.txt` only (trips per date; no stop_times). The v2 build leaves out the whole sidecar period when `holiday` is true, plus any same-period legacy change file (read from the same date), and lists it in the build report as `droppedHolidayPeriods: [{slug, periodKey, refDate, reason, routesAffected}]`. A sidecar without the field is kept. The shared picker is untouched. Rule: flag when (a) refDate's own trips are under 60% of the median of its day type, or (b) refDate is in Dec 20 - Jan 6 AND either its own trips are under 90% of that median, or a Mon-Fri date within 3 days of it (the dates the weekday reading uses) has under 85% of the median weekday's trips. Comparison days under 25% of the day type's 90th-percentile trips are stub days (leftover boat/rail service from an older period; MBTA's Aug 2016 feed had 121 of 230 weekdays at 64 trips against ~17,900) and are ignored, so a stub-heavy median cannot make a Christmas-week date look normal; with too few full-service days it falls back to all days. A holiday-window refDate with normal trips everywhere is kept; with fewer than 3 comparison days or a refDate outside the calendar, nothing is flagged. Thresholds come from the pilots: STM's Jan 5 2025 and Jan 4 2026 points have a normal own-day count (99%) but Jan 1 / Jan 2 weekdays at 64-67% of the median weekday; STM's five Thanksgiving-Monday refDates (2019 to 2023) sit at 69-76% of the weekday median with clean data (0 or 1 routes at 1.5x both neighbours), so a 70% own-day threshold would wrongly drop 2021 and (a) is 60%; MARTA and Denver sit at 100% everywhere. Result on the pilots: STM 2025 (dataset 20241028) and the Jan 2026 point (20251113) are dropped, so STM goes from 11 to 10 real years (still eligible, with no margin) and 2025 disappears; MARTA and Denver drop nothing. Existing sidecars get the field through `pipeline/recompute-history-ref-quality.ts --sidecar-dir --zip-dir --out-dir` (writes copies; originals are never touched). Caveats: sidecars are immutable, so the sidecar already in R2 for a period stays without the field until it is replaced; a feed with `calendar.txt` where the processor already moved to a typical week can still be flagged (blank, not wrong); regional holiday weeks outside Dec 20 - Jan 6 are not detected.
*   **Re-picked reference dates (v2 backfill, flag-gated).** Dropping a holiday-week period loses a whole year, so `backfill-history-v2.ts` (only with `ATLAS_HISTORY_V2=1`) first asks `pipeline/historyRefRepick.ts` whether the shared picker's date reads a normal week; if not it reads the SAME feed again at the nearest normal week of that feed (a real date, no data invented) and records it. The shared picker (`detectReferenceDate`) is untouched; the only shared-file change is an optional `referenceDate` process option (`process-core.ts`, one line, unset everywhere else) that lets the backfill hand the processor the new date. What counts as not normal: (a) the existing holiday rule above; (b) **Thanksgiving week**: the weekdays the processor reads (within 3 days of the date) touch the Mon-Sun week of the fourth Thursday of November AND a read weekday has under 85% of the median weekday's trips (MBTA's Fri 2018-11-23 and 2022-11-25 read the holiday Thursday, and one-off replacement ids instead of the main service: route 39 read Mon 252 / Tue-Wed 46 / Thu-Fri 0 trips and came out limited); (c) **split week**: among routes with at least 4 trips, the share whose median of the five read weekdays is under 50% of their busiest weekday is at least 5% and 3 points above the feed's own typical share (median over its normal weeks). A single low day (Canadian Thanksgiving Monday, Columbus Day) does not move a median of five, so STM's Monday-holiday periods (2019-2023) are not touched. The processor's reading is mirrored with its own `getActiveServiceIds` on the five weekdays, because MBTA's Thanksgiving week keeps normal trip totals per calendar date while the processor reads the wrong service ids. **Candidate weeks** are the Thursdays whose Mon-Sun week lies inside the feed's window, has trips on all five weekdays, holds no fixed holiday (New Year, MLK, Presidents, Easter weekend, Victoria, Memorial, Juneteenth, Canada Day, July 4, Labor, Columbus/Canadian Thanksgiving, Veterans, Thanksgiving, Christmas, Boxing Day) and misses Dec 20 - Jan 6; every weekday total must be 90-115% of the feed's typical weekday (stub weeks under 25% of the 90th-percentile week are ignored, as in the holiday rule) with a split share within 2 points of typical, and the re-run holiday rule must pass. The nearest candidate to the original date wins; a Thursday is used because the processor then reads exactly that Mon-Sun week. No candidate (calendar_dates-only feed inside the holidays, a feed window that is only the holiday week): the period keeps its date and is dropped as before. Thresholds come from the pilots: normal reference weeks sit at 0-1.4% split routes (STM 2019 is the worst at 1.4%, MARTA 0.8%, MBTA 0%), the worst single normal candidate week is 4.1% (STM), and the 2014 MBTA Christmas week is 50%; MARTA, Denver, LA Metro, Community Transit and IndyGo flag nothing except IndyGo's Jan 2 2024 period, which the holiday rule already dropped. Not re-picked: feeds that read the run date (`referenceDateFromRunDate`) or next-service dates. The sidecar stores `refDate` = the new date and `refDateQuality.repicked: {from, to, reason, fromYear, toYear, tripsOnFrom, tripsOnTo}`; the build report lists `repickedPeriods: [{slug, periodKey, from, to, fromYear, toYear, reason, tripsOnFrom, tripsOnTo, routes}]` next to `droppedHolidayPeriods`. A re-pick can move a period into another year (STM's Oct 2024 dataset: 2025 -> 2024) and so change which sidecar wins a year (one winner per year, latest refDate); read `fromYear`/`toYear` in the report. The `refresh` writer cannot re-read the feed (it reuses the live map's geojson), so it only applies checks (b) and (c): a flagged week is stored `holiday: true` and the build drops it. `recompute-history-ref-quality.ts` cannot re-pick either (that needs reprocessing); re-run the backfill. Flag unset: nothing changes.
*   **Storage.** Immutable sidecar objects `history-v2/{slug}/{periodKey}.json` (all routes of one agency period). Per-route archive files are untouched; `build-history` joins by period key, never by label. A sidecar with the same key and different content is a conflict, not an overwrite.
*   **Change detection.** The fingerprint is weekday + Saturday + Sunday headlines; unknown is a wildcard, so an old baseline against a new snapshot is not a change. `latest.json` gains `sat`/`sun` (and `wk`, marked `v: 2`).
*   **Visibility report (report-only).** `visibility` in the build report lists per agency: (a) current routes with no kept snapshot in the last 5 years, (b) history keys that match no current route (candidate split or renumbered keys; aliases count as a match), (c) spikes, a weekday value at least 5x both the previous and next kept snapshot (route, label, values). Nothing is dropped, hidden or changed by it.
*   **Writers.** `refresh` writes v2 only with `ATLAS_HISTORY_V2=1` (opt-in); so does `build-history` (see the gate above). `pipeline/backfill-history-v2.ts` rebuilds sidecars from archived zips into a local `--out-dir` and never touches R2.
*   **Supplemental (rail) feeds.** Agencies with `supplementalFeedUrls` (lacmta, nfta, septa, wmata, mta-maryland): with `ATLAS_HISTORY_V2=1`, `refresh` also puts the supplemental feeds' routes in the sidecar, each built with its own feed's calendar evidence, and lists them in the sidecar's `supplementalRoutes` (feed url -> route keys). Rail routes enter History from the first snapshot actually held: no invented history, no stitching of old keys (e.g. LA Metro 2013/14 rail 801-806 stay unaliased). A route key used by both the main and a supplemental feed is never overwritten: the main route is kept and the clash is printed in the refresh log. Supplemental feeds have no archive, so `backfill-history-v2.ts` refuses these agencies unless `--bus-only` is passed; the run then uses the main feed only and its report carries `busOnly: true`, `supplementalExcluded: [urls]` and "bus feed only; supplemental routes excluded". The build report's per-agency `visibility.supplementalFeeds` gives `{url, includedInHistory, firstSnapshot}` and a log line names each feed still not in History (report only; nothing is hidden). That line lists current routes with no history, which can include bus routes, since the artifact does not say which feed a route came from.

### History v2 reader contract

What the UI reads and how. Code: `shared/historyV2Reader.ts` (pure parsing and selectors), `src/utils/historyV2Loader.ts` (thin fetch layer).

*   **Files.** (1) Sidecar `history-v2/{slug}/{periodKey}.json`: `{version: 2, slug, periodKey, refDate, routes: {routeKey: {name?, rep, sat?, sun?, flag?}}, supplementalRoutes?}`, all routes of one agency period; a build input, not served publicly. (2) Agency-level history: `{slug, routes: [{routeShortName, routeName, snapshots: [{label, year, weekdayHeadwayMin, periodKey?, v2?}]}]}`, the `build-history` output and the shape of one `history-config.json` entry (`parseHistoryAgencyV2` accepts both).
*   **Three dates.** `refDate` is the real service day the processor read (YYYYMMDD). `year` is the year of `refDate` (v2) and is what the year slider uses. `periodKey` is only the archive file key (it can sit in another year than `refDate`); never show or sort by it when `refDate` exists.
*   **One snapshot per route per year.** The build keeps a single snapshot per (route, year). `routesForYear(agency, year)` returns exactly the routes that have one that year, each with that snapshot, its `periodKey` and `refDate`. A route with no snapshot in a year is absent from that year's list: the map shows only those routes for that year. `yearsAvailable(agency)` lists the years with at least one snapshot.
*   **Values.** `snapshotValue(snapshot, 'weekday' | 'sat' | 'sun')` returns `{kind:'value', min}`, `{kind:'limited'}` (no all-day value), `{kind:'none'}` (the feed positively has no service that day: stored `{none:true}`) or `{kind:'blank'}` (unknown: key absent). Weekday comes from `rep.h` / `rep.lim`; weekend from `sat` / `sun`.
*   **Never 0.** Zero is never stored and never shown for unknown. Blank is not none; none is not 0. Do not fill a blank from another day, another year or `headwayByPeriod`.
*   **Flags are stored, not hidden.** `snapshotFlag(snapshot)` gives `fast` (under 2 min), `slow` (over 300 min) or `limited`. The UI may word or mark them but must not drop the route or value because of one.
*   **v1 fallback.** A snapshot without `v2` (old data): weekday = `weekdayHeadwayMin`, Saturday and Sunday = blank, no flag, no `refDate`.
*   **Errors.** `parseHistoryV2Sidecar` and `parseHistoryAgencyV2` never throw; they return `{ok:false, error:{code, path, message}}` with code `not-object | unsupported-version | missing-field | bad-field`. Unknown extra fields are ignored and kept, so newer data does not break old readers; a newer sidecar `version` is rejected rather than guessed at.
*   **UI must not.** Treat missing weekend data as 0 or "no service"; hide fast/slow/limited routes; infer the year from the label or `periodKey`; show routes for a year that has no snapshot; read local paths in a built site.
*   **Route shapes.** A route's line for a year comes only from `shapeForYear` (see "History v2 route shapes"); `{kind:'none'}` means the shapes file has no line for that route that year; the reader never substitutes anything. The UI chooses the fallback: a route with no shape that year is drawn with today's line for that route, and the latest year always uses today's map.
*   **Local fixtures (no R2).** `npm run history-v2:fixtures` copies the pilot outputs (marta, rtd-denver, indygo, lacmta) from the scratchpad into `tmp/dev-history-v2/` (gitignored; never committed). Then run the app with `VITE_HISTORY_V2_BASE=/dev-history-v2` (for example `VITE_HISTORY_V2_BASE=/dev-history-v2 npm run dev:beta`). Vite dev serves `tmp/dev-history-v2` at `/dev-history-v2`: agency files at `/dev-history-v2/{slug}-v2-agency.json`, sidecars at `/dev-history-v2/history-v2/{slug}/{periodKey}.json`. `loadHistoryAgencyV2(slug)` and `loadHistoryV2Sidecar(slug, periodKey)` use it when set. The override is read only when `import.meta.env.DEV` is true, so built sites ignore it (same pattern as `ON_DEMAND_URL_OVERRIDE`), and the server route exists only in `vite` dev. Without it the loader takes the agency from `history-config.json`.

### History v2 route shapes (flag-gated; per-year lines)

Scrolling History back to a year shows the map as it was that year, so each year needs its own route lines. Code: `pipeline/historyShapes.ts` (extract, simplify, dedupe), `shared/historyV2Reader.ts` (`parseHistoryShapes`, `shapeForYear`, `shapeYears`), `src/utils/historyV2Loader.ts` (`loadHistoryShapesV2`). Ticket: CIV-455.

*   **Gating.** Shapes are written only by the v2 backfill (`backfill-history-v2.ts --shapes`, off by default) and joined only by `build-history` under `ATLAS_HISTORY_V2=1`. Unset, the build neither lists nor reads shape objects and publishes nothing new; `history-config.json` is byte-identical to origin/main either way (`buildHistoryDefaultGolden.test.ts` also asserts the only R2 write is `atlas/history-config.json`). Snapshots never carry shape data; their old v1 `geometry` field stays readable and is untouched.
*   **Extraction (per archived zip).** One representative line per route key (same `historyRouteKey` as the snapshots, long-name fallback on). Pool the trips of every route_id with that key, take direction 0 (else the lowest direction that has a shape), drop short turns (shapes under 75% of the longest, as `shape-selection.ts` does), then take the shape most trips use (ties: longer). Points come from `parseGtfsZip` (so the same jump repairs as the map). A route with no usable shape in any direction (or a feed with no shapes.txt) gets a line through the stops of its direction-0 trip that serves the most stops, in stop_sequence order, flagged **approximate** (straight links between stops; the UI should say so or style it differently). Fewer than 2 located stops: no shape, the year reads `none`. Weekend-only and day-type are not considered (the snapshot already requires a weekday value).
*   **Simplify and round.** Douglas-Peucker (`geometry.ts` `simplifyLine`) in metres via a local projection, tolerance `HISTORY_SHAPE_TOLERANCE_M = 15`, endpoints kept, then rounded to `HISTORY_SHAPE_DECIMALS = 5` (about 1.1 m) with repeated points removed. Both are single named constants stored in the files (`toleranceM`, `decimals`); a different value is a different object (conflict, not an overwrite) and `compileAgencyShapes` refuses to mix them. The map's own artifacts use about 11 m (0.0001 degrees); 15 m is a little coarser because the History map is a regional view.
*   **Storage.** Two files, neither in `history-config.json`:
    1.  Archive (private) `history-v2-shapes/{slug}/{periodKey}.json`: `{version:1, slug, periodKey, refDate, decimals, toleranceM, routes:{key:{c:[[lon,lat],...], a?:true}}}`, immutable like a sidecar. A separate prefix on purpose: `build-history` lists `history-v2/` and would parse a `.shapes.json` there as a sidecar. Routes with no shape are absent.
    2.  Public `atlas/history-v2-shapes/{slug}.json` (compiled by `build-history`): `{version:1, slug, decimals, toleranceM, shapes:[[[lon,lat],...],...], approx?:[index...], years:{"2014":{routeKey:index}}}`. Every distinct line is stored once (content hash of the prepared line, sha-256) and each (year, route) points at it by index. A year's entry comes from the period of that year's kept snapshot, taken before the change-only filter (so every year the build kept gets a line even where the route's headway did not change, and line and headway come from one feed), looked up under the canonical key first, then its aliased old keys. A route-year with no stored line is simply absent.
*   **Why this layout.** (a) Not in the snapshots: one agency's shapes (0.5 to 0.9 MB raw) are 1 to 2 times its snapshots (0.43 to 0.50 MB raw for the three pilots), and the screen loads snapshots eagerly. (b) Not per year: dedupe works across years only inside one dictionary, and the file is small enough (below) that one lazy fetch per agency, when History opens that agency, beats a request per scrolled year. (c) Indexes, not hash strings, in `years`: hash strings make that map about 2.6 times larger raw (13 KB against 35 KB for MARTA). (d) Not inside the sidecar: sidecars are read by every v2 build and must stay small and unchanged.
*   **Reader.** `shapeForYear(shapes, routeKey, year)` returns `{kind:'shape', coordinates, approximate}` or `{kind:'none'}`. `none` covers a missing file, year or route and means "no shape stored for this year"; the reader itself never falls back to today's geometry, another year's line or a snapshot's old `geometry`. The fallback is the UI's choice: a route with no shape that year is drawn with today's line for that route, and the latest year always uses today's map. `routeKey` is the route's `routeShortName` in the agency file. `parseHistoryShapes` never throws, checks every line and every reference, and rejects a newer `version` as `unsupported-version`; unknown extra fields are kept. If the shapes file is absent (not built yet) `loadHistoryShapesV2` returns `{ok:false}` and every route reads `none`.
*   **Every year a route ran (v2, flag-gated).** Under `ATLAS_HISTORY_V2=1` the build keeps one snapshot per route per year for every year in which the route has a kept v2 sidecar entry with a weekday value, whether or not its headway changed, so `routesForYear` lists every route that ran and the shapes file has a line for each. Rules: (a) a snapshot that came from a sidecar is never dropped for equalling the previous one (`filterSnapshotsForPublish`); (b) a route whose first and last value are equal is no longer left out when it has a sidecar-backed snapshot (`isFlatRouteToSkip`); (c) a route absent from a year's sidecar is absent that year; a limited or blank weekday is still dropped (`no weekday headline` in the build report), never filled in; holiday-week sidecar periods are still dropped whole; one winner per year is unchanged; (d) a route with a single point is kept when that point is sidecar-backed (one sidecar year and no current endpoint: it ran in that year, so it is listed and drawn), and the legacy "at least 2 snapshots" rule applies only to flag-off builds and to routes with no sidecar-backed snapshot (a v1-only single snapshot is still dropped). **Size of (d)** (pilot sidecars, current endpoint approximated from the live config; history-config snapshots only, shapes file not re-measured): single-point routes added, snapshots, raw and gzip bytes versus keeping the 2-snapshot rule: MARTA +20 routes (123 to 143), +20 snapshots, +7.6 KB raw, +0.4 KB gzip; RTD Denver +22, +22, +8.5 KB, +0.6 KB; IndyGo +1, +1, +0.4 KB, +0.02 KB; LA Metro bus +47, +47, +18.3 KB, +1.4 KB; STM +17, +17, +6.6 KB, +0.6 KB. **Limit:** only periods with a v2 sidecar get this. The old per-route change files record changes only, so for a v1-only period the build cannot know the route ran in an unchanged year; those keep the change-only rule and nothing is invented (blank beats guessed). A route's earlier years stay sparse until that period is backfilled through v2. Flag unset: unchanged (change-only), byte-identical to origin/main.
*   **No compact encoding.** Snapshots are stored plainly; there is no "same as previous year" marker, so the reader (`routesForYear`, `yearsAvailable`, `snapshotValue`) needed no change. Measured on the pilot sidecars (aliases applied, no current endpoint; raw / gzip bytes, change-only vs every year): MARTA 403 snapshots 147 KB / 10.7 KB vs 1,397 snapshots 491 KB / 22.7 KB; RTD Denver 173, 65 KB / 5.2 KB vs 1,218, 435 KB / 20.0 KB; IndyGo 61, 22 KB / 2.1 KB vs 427, 150 KB / 6.9 KB; LA Metro bus 559, 202 KB / 15.2 KB vs 1,136, 405 KB / 25.0 KB; STM 819, 289 KB / 22.6 KB vs 1,911, 669 KB / 41.6 KB. Routes listed grow too (MARTA 103 to 123, Denver 60 to 145, IndyGo 20 to 39, LA 126 to 165, STM 144 to 190). Over the wire it is 5 to 19 KB more per agency, so a run-length encoding would save a few KB at most and add a reader contract; not worth it.
*   **Current year.** The compiled file covers the years of archived snapshots. The build's current-year endpoint comes from the live artifact and has no archived period unless one exists in that year, so it reads `none`; the UI decides how to show the current map for that year.
*   **Pilot measurements (local zips; `scripts/history-v2-pilot-shapes.ts`).** Per agency, 15 m / 5 decimals (recommended): MARTA 0.93 MB raw, 243 KB gzip, 77 KB brotli, 908 stored lines for 1,417 route-years; RTD Denver 0.62 MB, 138 KB, 46 KB, 578 lines for 1,240; LA Metro bus 0.48 MB, 110 KB, 32 KB, 484 lines for 1,183. All 3,840 route-years had a shape (every pilot feed has shapes.txt, so no stop-derived lines occurred). Identical-line reuse is 1.6x (MARTA), 2.2x (Denver) and 2.4x (LA): lines change between feeds more often than routes do. The live `history-config.json` carries geometry on only 6 of 423 MARTA, 48 of 300 Denver and 67 of 616 LA Metro snapshots (8.9, 60 and 63 KB), so per-year shapes are a new, larger payload rather than a replacement; the old `geometry` fields can be dropped from a v2 build once the UI reads shapes.
*   **Fixtures.** `npm run history-v2:pilot-shapes -- --pilots` builds the pilots' shapes from the local zips (writes `{slug}-v2-shapes.json` and `history-v2-shapes/{slug}/` beside each `{slug}-v2-agency.json`; add `--raw-cache <dir>` to skip re-parsing, `--tolerance-m` / `--decimals` to try other settings); `npm run history-v2:fixtures` then copies `{slug}-v2-shapes.json` into `tmp/dev-history-v2/`, served at `/dev-history-v2/{slug}-v2-shapes.json`. With `VITE_HISTORY_V2_BASE=/dev-history-v2`, `loadHistoryShapesV2(slug)` reads it. Real archive runs: `npx tsx pipeline/backfill-history-v2.ts --slug <slug> --zip-dir <zips> --out-dir <dir> --shapes` (local only; uploading is a separate, approved step).

### Publishing History v2 (runbook)

Tooling (CIV-446): `npm run history:backup`, `history:restore`, `history:upload`. All three are script-only, dry-run by default, and mutate only with `--write`, which also needs `ATLAS_HISTORY_V2=1` in the environment (they refuse otherwise). None is called by `refresh`, `build-history` or any workflow. Per `CLAUDE.md` "Confirm before writing to R2": **every `--write` below needs Ryan's explicit go-ahead, with what and why stated first.** A past approval or a clean dry run is not approval.

Secrets, by name only (in `.env.local` of the main checkout; a worktree's `.env.local` is key-free on purpose, so run real steps from the main checkout): `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME` (public bucket; backup/restore and the build's public writes), `R2_ARCHIVE_BUCKET_NAME` (private bucket; upload), `R2_PUBLIC_URL` (used by the build). Without credentials a dry run prints the plan from local files and says `remote state unknown (no credentials; dry-run listing skipped)`.

**Order**

1.  **Merge the code to main.** `ATLAS_HISTORY_V2` stays unset in every workflow, so the weekly cron keeps publishing the v1 output (byte-identical, see the gate above).
2.  **Local dry run per agency** (no R2 access needed):
    `npx tsx pipeline/backfill-history-v2.ts --slug <slug> --zip-dir <zips> --out-dir tmp/history-v2 --shapes` (with `ATLAS_HISTORY_V2=1` so holiday and Thanksgiving weeks are re-picked; add `--bus-only` for agencies with supplemental feeds), then
    `npm run history:upload -- --slug <slug> --dir tmp/history-v2` (dry run). Review `tmp/history-v2/<slug>-report.json` and the upload plan: periods with a holiday reference date and no repick are listed as SKIPPED (the build would drop them), re-picked periods are listed in the report, key and byte totals, and any `CONFLICT`. One agency per run.
3.  **Back up the live config** (public bucket): `npm run history:backup` (dry run, prints keys, size, sha256, agency count), then, with Ryan's go-ahead, `ATLAS_HISTORY_V2=1 npm run history:backup -- --write`. Writes `atlas/history-config.backup-YYYYMMDD-HHMMSS.json` plus `.manifest.json` (sourceKey, sizeBytes, sha256, createdAt, agencyCount, gitCommit, hash and slug list of `shared/data/history-agencies.json`). Backups are immutable (an existing key is refused), and the copy is read back (size + sha256) before the manifest is written. Note the stamp it prints.
4.  **Upload one agency at a time** to the private bucket, with Ryan's go-ahead for each: `ATLAS_HISTORY_V2=1 npm run history:upload -- --slug <slug> --dir tmp/history-v2 --write`. New keys are put, identical existing content is a no-op, different content is a CONFLICT: all keys are checked before the first write, any conflict stops the run with a non-zero exit and nothing written (a race mid-run stops at once). Nothing is ever overwritten. `--period <periodKey>` limits a run. Every local file is validated first (sidecar parser, slug and periodKey must match the path); one bad file refuses the run.
5.  **Build** (public bucket, goes live immediately): `ATLAS_HISTORY_V2=1 npm run build-history -- --dry-run` first (writes `tmp/history-config.dry-run.json`, `tmp/history-v2-shapes/` and `tmp/history-build-report.json`; review drops, holiday and re-picked periods, visibility), then with Ryan's go-ahead `ATLAS_HISTORY_V2=1 npm run build-history`. It rewrites the **whole** `atlas/history-config.json` (every agency, not only the uploaded ones) and writes the public `atlas/history-v2-shapes/{slug}.json` files; the live History app reads the new config at once. It also rewrites `shared/data/history-agencies.json` locally with `realYearsOnly`.
6.  **Commit `shared/data/history-agencies.json`.** The list shrinks from 22 to 16 (real snapshot years only). The 22 today: brampton, burlington, caltrain, cdta, communitytransit, ddot, gcrta, grt, halifax, indygo, kingston, lacmta, marta, metro-transit, metrostlouis, miami-dade-transit, nfta, rtd-denver, sacrt, spokane, stm, wrta. The 6 that drop are set by the real build (they are the ones whose years came from `coverage.json`); read them from `git diff shared/data/history-agencies.json` and record them in the commit message. The dry run does not write this file.
7.  **Post-checks:** fetch `atlas/history-config.json` and a shapes file from the public URL and parse them (`parseHistoryAgencyV2`, `parseHistoryShapes`); open History for 2-3 agencies on localhost; confirm the agency count in the file against the list; `npm run build-history -- --verify-only` with the flag.

**Rollback**

*   Sidecars and shapes archive files are new immutable keys in the private bucket. The old v1 per-route files are never touched, so there is nothing to undo there; leaving the sidecars in place is harmless (a build without the flag does not list or read them).
*   To undo the live config: `npm run history:restore -- --from <stamp>` (dry run shows sizes, sha256, agency counts and which agencies differ), then with Ryan's go-ahead `ATLAS_HISTORY_V2=1 npm run history:restore -- --from <stamp> --write`. It first makes its own verified backup of the current file (`atlas/history-config.pre-restore-<stamp>.json` + manifest), writes the backup's exact bytes, and reads them back. It checks the backup against its manifest first and refuses a mismatch. It does not touch `shared/data/history-agencies.json`: revert the agencies-list commit with git. The public `atlas/history-v2-shapes/{slug}.json` files are not removed (nothing reads them without the v2 config; delete them by hand only if wanted).
*   **The weekly cron undoes v2 unless the flag is set in the workflow (open decision for Ryan; workflows were not changed).** `refresh-feeds.yml` runs `npm run build-history` every Monday with no `ATLAS_HISTORY_V2` (no workflow sets it), and `rebuild-release.yml` runs the same step (also writing `history-config.json` live, before its publish step). With the flag unset, `build-history` lists no sidecars, joins no v2 data, drops no future or blank snapshots, writes no shapes files and rewrites **the whole `atlas/history-config.json` as v1, built from the per-route change files**. So the first Monday after the publish silently replaces the v2 config with v1 (and refresh also stops writing sidecars, so new periods get none). The old public shapes files would remain but nothing would point at them. For v2 to persist, `ATLAS_HISTORY_V2: '1'` has to be set on the `Rebuild history config` step (and on the `refresh` step so new periods get sidecars) in both workflows, and the committed `history-agencies.json` must be the v2 one. Until that is decided, either accept that the cron reverts v2 weekly or do not publish. Whether to set it, and when, is Ryan's call.
*   Rollback while the flag IS set in the workflow: restoring the config is not enough, because the next Monday rebuilds v2 again from the sidecars. Unset the flag in the workflow first (or the weekly build puts it back); only then does leaving the sidecars in place do nothing. Deleting sidecars is not needed for rollback and is not supported by these tools.

**Not verified without R2:** the real key listing and ETag behaviour (the manifest records an `etag` only if the client returns one; the current `r2Get` helper does not, so it is omitted today), the exact byte-for-byte round trip of `r2Put` (the read-back check exists to catch this), and that the `atlas/history-config.backup-*` keys do not trip any prefix scan of `atlas/` in the app (none found in `pipeline/` or `scripts/`).

### Data sourcing
Historical snapshots are compiled via two methods:
1.  **Weekly Snapshots (Automated)**: Since the pipeline's launch, weekly runs (`refresh.ts`) automatically archive headway changes under `history/{slug}/{routeShortName}/{periodKey}.json` in `atlas-archive`.
2.  **Historical Backfilling (One-off)**: Running `pipeline/backfill-mdb-history.ts` fetches dataset archives from the **Mobility Database (MDB) API** dating back to ~2013-2016, processes them chronologically, and writes the snapshot history.
